# API Contract

## Base URL

The browser talks to the backend through:

```text
http://localhost:4000/api
```

The production value must be supplied through `VITE_BACKEND_URL` in the frontend environment. The Express application mounts the API prefix in `backend/src/app.ts`.

## Planned resource operations

The following operation names describe the intended contract, not completed endpoints:

| Resource | Expected operations |
|---|---|
| Auth | register, login, current user, logout/refresh |
| Items | list, detail, create report, update status, attach images |
| Claims | create claim, list mine, review claim, approve/reject |
| Threads | get thread, add comment, moderate comment |
| Notifications | list unread/read, mark read |
| Vault | intake item, list custody, create handover, release item |
| Admin | manage users/categories/records, inspect audit log |

When implementing one of these, choose resource-oriented paths and HTTP methods consistently, for example `GET /items`, `GET /items/:itemId`, and `POST /items`. Document the final path here before wiring frontend calls.

## Request conventions

- JSON requests use `Content-Type: application/json`.
- Resource identifiers are opaque string IDs generated by Prisma (`cuid()`).
- Authentication must be established before protected operations. The transport (session cookie or bearer token) is not implemented yet; decide it explicitly and document it before adding middleware.
- Role checks must be enforced server-side. Frontend `RoleGuard` is only a UX boundary.
- Image fields should remain references/URLs in JSON; binary upload handling needs a documented storage provider and upload strategy.
- Validate all client-provided strings, IDs, enum values, and image references at the API boundary.

## Response conventions

Success responses should be JSON and use the resource shape described by the endpoint. Collection endpoints should return a stable collection property and pagination metadata once pagination is introduced.

Errors should:

- Use an appropriate HTTP status (`400`, `401`, `403`, `404`, `409`, or `500`).
- Return a stable machine-readable error code.
- Include a human-readable message safe for the client.
- Avoid leaking passwords, hashes, hidden item details, or internal stack traces.

The existing error middleware is the place to normalize uncaught errors. Keep feature-specific validation close to the feature.

## Contract change checklist

Before changing an API:

1. Identify the owning feature router.
2. Define auth and role requirements.
3. Define request and response JSON examples.
4. Define validation and conflict behavior.
5. Update this document and the frontend caller together.
6. Add tests for success, unauthorized, forbidden, invalid, missing, and conflict cases where applicable.
